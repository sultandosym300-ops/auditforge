# Submission manifest

The final ZIP is generated by `python -m scripts.package_submission`. It contains executable source, a pinned frontend lockfile, Dockerfiles, documentation, schemas, ten generated train companies, ten generated dev companies, trusted evaluator references, three public-policy trajectories per train company, all four trusted-host baseline results and reproducible current audit reports.

The `datasets/train/public` and `datasets/dev/public` trees contain only public manifest/policy, ledger, invoices, payments and FX data. The corresponding `evaluator_private` directories contain truth and provenance for the trusted evaluator; never mount them into the policy container. Ordinary trajectories do not include oracle reference answers.

Excluded: `.git`, assistant/hosting metadata, credentials, filled env files, dependencies, virtual environments, caches, runtime accounts, working logs, existing archives, generated web/Python builds and unrelated local files. The blank `.env.example` is allowed. Source files and example assets needed to reproduce the website remain included.

Every package receives `submission-manifest.json`: exact relative path, size and SHA-256 for every payload file, plus source commit/dirty-state provenance when available. The manifest excludes its own digest to avoid a circular hash. This Markdown file is expanded with the complete file inventory during packaging. The checker verifies exact file-set equality, not just listed-file presence.

A final archive is ready only after its own extracted contents pass `submission_check`, regression tests, documented startup and the required container checks. Packaging success alone is not a claim that Docker ran or that the archive received an official jury score.
