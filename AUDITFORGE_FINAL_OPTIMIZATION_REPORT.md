# AuditForge · измеренная оптимизация политики исследования

## A. Исходное состояние

Контрольный коммит 1db02796f95e78b4520c528727c45240d64ee6c0 сохранён тегом auditforge-pre-optimization. Исходные 118 тестов прошли. В проекте проверены генератор, Session/AuditEnv, matcher, reward, независимый Fraction-аудитор, четыре базовые политики, shortcut-диагностики, сайт, Supabase Auth и локальная Training Lab. Нормативный источник — опубликованный FinTech-кейс из материалов пользователя, разделы 03–07 и 10.

Исходная пятикомпонентная логистическая политика по одному запрашивала счета. Исторический эксперимент 314159/300/40 воспроизводится отдельно, исходник baseline хранится с SHA256 в scripts/controls/training_201.py. Генератор, основной matcher, reward и официальный API сохранены. Реальные секреты в Git не включаются; publishable-ключ Supabase предназначен для браузера.

## B. Дефекты и исправления

1. После первой неудачи загрузки Python worker навсегда хранил отклонённый promise. Повтор запроса не восстанавливал лабораторию. Теперь при отказе инициализации runtime очищается, следующая попытка повторяет загрузку. Регрессия scripts/check_worker_retry.mjs моделирует отказ, успешный повтор и повторное использование среды.
2. Источники документов открывались по одному, хотя контракт позволяет страницы до 50 записей. Это ограничение политики увеличивало стоимость period до 45 действий. Новая модель выбирает получение источников страницами.
3. Three.js, EvidenceCore и Training Lab входили в первоначальный граф загрузки. Введены разделённые чанки, отложенное монтирование EvidenceCore при приближении секции и Training Lab после открытия вкладки. Текущее состояние модели сохраняется при смене вкладки.
4. График рисовал каждую точку неограниченной истории. Сейчас отображается не более 501 точки с сохранением экстремумов, полная история остаётся в checkpoint.
5. Некорректный checkpoint с пустой строкой истории проходил импорт и мог обрушить график. Загрузчик V1/V2 теперь проверяет последовательность эпизодов, конечные метрики, диапазоны, измерения и бюджет. Регрессия воспроизводит дефект.
6. Убрано повторное заглавие Training Lab. Это ограниченная правка существующей иерархии страницы.

## C. RL-исследование

Рассмотрены исходная логистическая политика, иерархическая логистическая политика, MLP, Actor-Critic и PPO. Полные измерения сделаны для первых двух архитектур и learning rate 0,1/0,3/0,6. Для MLP, Actor-Critic и PPO не заявляется экспериментальное превосходство или проигрыш: для трёх ограниченных решений их дополнительная сложность не понадобилась.

Кандидат обучает 21 вес трёх логистических шлюзов получения invoices/payments/fx. Признаки — кратность расходных записей, положение относительно границ периода, иностранные платежи, расхождение распределения, оставшийся бюджет и bias. Все признаки вычисляются только из уже полученных наблюдений. Последующий шлюз может использовать ранее полученные источники.

REINFORCE обновляет веса по терминальному reward с moving baseline. Никакой подстановки F1 и teacher warm-start нет. Пагинация выбранного источника и сборка документального доказательства детерминированы. Модель обучается выбору источников, не нейронному вычислению суммы или генерации текста. Это граница между обучением и финансовой логикой, отражённая в UI.

Сначала learning rate выбран на 30 development mixed-компаниях. Все три кандидата дали равный reward, детерминированная ничья выбрала 0,1. Основной holdout — три seed обучения 314159/271828/161803, по 50 новых компаний семи сценариев. Предсказания трёх моделей на одной компании зависимы; bootstrap группирует их по компании. Все 5250 основных запусков сохранены в JSON и CSV.

## D. Измерения

Полная таблица F1/P/R/reward, шагов, median/p90, времени, стандартных отклонений и pooled TP/FP/FN находится в reports/optimization-summary.md и reports/optimization-benchmark.json. Ниже ключевые результаты, вычисляемые из тех же данных. Метрики не меняют официальный максимум 100.

Проверены period, duplicate, FX, allocation, mixed, clean и компенсирующиеся ошибки. Кандидат сохраняет F1=1 на всех семи измеренных сценариях и не выдаёт ложных находок на чистых компаниях. Базовая политика не ухудшалась искусственно. Для FX и allocation она ограничена своей исходной архитектурой.

В period новая политика использует 6 шагов с F1=1; ограничение 5 шагов даёт F1=0,2 за счёт чистых компаний. Это практическая граница исследованной архитектуры с чтением всей книги, не глобальная нижняя граница. Для mixed новая политика требует 10 шагов и достигает качества фиксированной сверки.

Отдельные 144 проверки используют иные размеры 41/50/84/200, смещения, даты, переименование ID и перестановки. Все прошли, F1=1, максимум 33 действия. Новые комбинации проверены без дообучения и записаны в reports/optimization-generalization.json.

## E. Отрицательные контроли и ограничения

Замороженные исходные веса не обучаются и дают F1=0,2 на period. Контроли случайных весов и перемешанных наград иногда случайно выбирают правильные шлюзы: один из трёх seed дал F1=1. Поэтому эти опыты не доказывают, что успех невозможен без сигнала награды. Подтверждено реальное изменение весов, его воспроизводимость и полезное поведение, а не уникальность RL как способа поиска трёх решений.

На чистой компании молчание может быть дешевле приобретения документов. Размеры компаний основного сравнения ограничены 40 счетами, дополнительная проверка покрывает более крупные книги. Эффективность источников целиком не равна выбору наиболее полезного отдельного документа. Mixed inference новой модели медленнее старой неполной политики по CPU. Трассировка памяти также показывает большую стоимость кандидата.

На данных period кандидат выигрывает у фиксированной сверки по reward, потому что выбирает счета и не читает ненужные payments/FX. На mixed он соответствует фиксированной сверке по F1 и шагам. Это преимущество измерено на конкретных сценариях.

## F. Браузер, совместимость и проверка выпуска

Входной JS уменьшен с 1190,97 до примерно 645,57 KB, gzip с 339,04 до 197,80 KB. Общая загрузка первого экрана уменьшилась существенно меньше: Three.js всё ещё нужен герою. Выигрыш GPU или сетевого cold-start не заявляется. Измерения и ограничения содержатся в reports/frontend-performance.json.

V1 и V2 checkpoints распознаются по формату, несовместимая архитектура и нечисловые параметры отклоняются. Старый V1 продолжает обучение исходным алгоритмом. V2 использует новые шлюзы. Импорт не исполняет код. Worker включает тот же efficient_training.py, что Python; разница после 100 эпизодов между native/Pyodide меньше 1e-12. Время не сравнивается побайтово.

E2E прошёл создание компании, открытие записи и документа, обучение, остановку, продолжение, скачивание, перезагрузку, восстановление checkpoint, независимую проверку четырёх политик, запуск текущего эпизода, просмотр findings/траектории и отсутствие закрытых полей. Гостевой режим и Supabase Auth сохранены. Облачные credentials пользователя не использовались для автоматического тестового входа.

Пройдены 126 unit/integration/regression-тестов. Мутационный набор расширен обратным знаком градиента: он должен лишить модель подтверждённого улучшения на holdout. Полный Docker CI запускает регламентные проверки без сети на Python 3.11, 2 CPU, 4 GiB RAM, измеряет память и размер поставки и проверяет изоляцию политики.

Команды воспроизведения:

python -m scripts.optimization_benchmark

python -m scripts.optimization_generalization

python -m scripts.ultimate_verify --seed 605198374621

node scripts/check_worker_retry.mjs

npm run build

Исследовательская оптимизация увеличивает покрытие и эффективность ограниченной политики. Официальную оценку и место на хакатоне определяет жюри.
